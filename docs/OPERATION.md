# ワンセグ（ISDB-T 1seg）復調器 RTS_SDR — 仕様と使い方

最終更新: 2026-09-26（ライブ映像＋音声の復号を実測確認）
対象: `/home/dino/oneseg-rs`（Rust workspace）+ DS-DT308SV（RTL2832U + Fitipower FC0013）

---

## 1. 何をするソフトか

1seg（中央1セグメント）の IQ を入力すると、OFDM 同期 → チャネル等化 → TMCC 復号 →
デインタ → Viterbi → RS 復号 → MPEG-TS 出力までを一パスで行う。出力 TS は
ffplay / VLC でそのまま再生できる。ブラウザ版（WASM + WebUSB）も同じコアを使う。

フルセグ（約5.6MHz）は RTL-SDR の窓に収まらないので対象外。1seg（約700kHz幅）だけが
窓に収まり、かつスクランブルがかかっていないのでそのまま復号できる。

## 2. ハードウェア前提

| 項目 | 値 |
|---|---|
| チューナ | DS-DT308SV（`0bda:2832`、RTL2832U + Fitipower FC0013） |
| モード | `rtl2832_sdr` / `dvb_usb_rtl28xxu` を blacklist して `rtl_sdr` から使う |
| 受信例 | 札幌 NHK総合 ch15 = 485.142857 MHz（NHK教育 ch13 = 473.142857 MHz） |
| サンプルレート | **1015873 Hz**（実測 exact = 1015873.002204 Hz） |
| 変調パラメータ | Mode 3 / G1/8 / FFT_LEN 1024 / 中央432キャリア |

1seg の中央セグメントは全体8セグメント中1つで、帯域は約700kHz。1015873 Hz の窓に
完全に収まるのが部分受信（partial reception）。TMCC は全帯域共通なので Layer B/C も
読めてしまうが、実際に物理的に持っているのは Layer A だけ。

## 4. 使い方

### 4.1 ライブ再生（メイン用途）

```bash
# 周波数指定（札幌 NHK総合 ch15）。引数は [周波数Hz] [秒数、0=終了まで]
./scripts/live_play.sh 485142857

# 周波数省略 → 1seg 帯域の既知チャンネルを順に試してロックしたものを再生
./scripts/live_play.sh
```

Piping を手で組むなら:

```bash
cd ~/oneseg-rs
rtl_sdr -f 485142857 -s 1015873 -g 0 -  \
  | ./target/release/examples/stream_decode - - \
  | ~/.hermes/tools/ffmpeg-9.0.1-linux-x64/bin/ffplay - -autoexit
```

**Wayland セッションでは ffplay のウィンドウが出ないことがある。** Wayland のとき
SDL は Xwayland に落ち、`DISPLAY=:0` 経由の grab は真っ黒になる。これは復調の失敗
ではない。映像を客観的に確認したいときは SDL を介さず ffmpeg にフレーム化させる:

```bash
rtl_sdr -f 485142857 -s 1015873 -g 0 - \
  | ./target/release/examples/stream_decode - - \
  | ffmpeg -i pipe:0 -frames:v 6 -f image2 /tmp/live_%02d.png
```

- **bin offset は自動決定される**（`stream_decode` が `bin offset=NNN` を出力する）。
  capture ごとに数百Hz〜一〜二 bin ズレるため、308等の固定値で当てると信号部が全滅して
  RS 0% になる。`select_segment_offset()` が TMCC フレーム同期一致率（主）+ 既知
  キャリア位相スコア（同点割り）で決める。同期一致 95% 未満は偽ロックとして拒否する。

- `-g 0`（自動ゲイン）を使う。**手動ゲインを指定すると 8bit ADC が飽和して
  TMCC が壊れる**（後述 §6）。
- 再生は **ffplay 優先**。VLC は VA-API / X11 converter で数秒停止し、ログ上の終了は
  映像表示成功の証拠にならない。
- `stream_decode` は起動時に PAT/PMT/SPS/PPS/IDR を溜めてから出力するので、
  中途から join した player でも復号起点が取れる。

### 4.2 ファイルからバッチ復号

```bash
./target/release/examples/decode cap.iq 1015873 out.ts 12000
ffmpeg -ss 6 -i out.ts -frames:v 1 frame.png     # 映像を1枚抜く
```

### 4.3 受信状態の確認（最初に行う）

```bash
# 同期 → TMCC → BCH → Layer パラメータ
./target/release/examples/tmcc_probe cur.iq 1015873

# 「本当に1segが乗っているか」の最終判定。偽ロックを明示的に弾く
./target/release/examples/lock_search cur.iq 1015873 2000

# 同期語16bitの一致ヒストグラム。良品=1.00×16、偽ロック=散在
./target/release/examples/tmcc_bitdump cur.iq 1015873
```

## 5. ロックの判定基準（重要）

TMCC 同期語の一致率 **60〜75%（特に 68.8% = 11/16）は偽ロック**であり、
「信号が弱い」ではない。`find_frame_sync_joint` が 204 通りのフレーム位相から
一致ビット数の最大のものを選ぶため、**ノイズだけでも必ず 60〜75% に張り付く**。

`tmcc_probe` の判定は `FrameSync::is_true_lock()` を使う。真のロックは以下の4条件すべてを満たす場合だけ:

1. 同期語16bitが**全フレームで一貫**している（`consistent_sync_bits == 16`）
2. even/odd フレームが交互（`alternates`）
3. BCH(273,191) が OK
4. 一致率 95% 以上

偽ロックは 1・2・3 のいずれかを必ず落とすので区別できる。実測値:

| 入力 | 一致率 | 一貫ビット | alternates | BCH | 真のロック |
|---|---|---|---|---|---|
| 良品 `sapporo/lowgain/g0.iq` | 100% | 16/16 | true | OK | **YES** |
| 良品 `sapporo/connected.iq` | 100% | 16/16 | true | OK | **YES** |
| 熱ノイズだけの取り込み | 70% | 3/16 | false | NG | **NO** |

**偽ロックは復調器側の調整では絶対に直らない。** sync radius 4/8/16 × セグメント
bin offset 41通りを総当たりしても 70% が天井で、信号そのものが無いため demod する
対象が存在しない。C/N を確保するのはアンテナ／受信環境側の問題。

### 偽ロックを見分ける3つの方法

- **複数チャンネルで同じ値が出る** → 偽ロック。本物の1segならチャンネルごとに違う
- **セグメント bin offset がチャンネル毎に変わる** → 偽ロック。本物なら 308 で固定
- **1seg内 と guard帯の電力差** → 本物は約 3.9dB。熱ノイズだけだと 2〜3dB で頭打ち

## 6. 実運用上の落とし穴

- **手動ゲイン禁止**。`-g 17.9` / `-g 19.7` は 8bit ADC を飽和させ、入力の 18.75%
  （0 と 255 に集中）が潰れて TMCC が壊れる。`-g 0`（自動）が唯一正しい。
- **`No E4000 tuner found, aborting` は失敗ではない**。FC0013 成功後の E4000
  専用フォールバックメッセージ。
- **`timeout` で rtl_sdr を止めると終了が不安定**。IQ へ드는 `head -c` でクリーンに
  EOF させる。
- **低ゲイン群 `lowgain/` だけが 100% ロックした記録がある一方、同条件の
  `gain-test/`・`scan/` は全て偽ロック。ゲイン方向の差は ADC 飽和で説明できる。
- ログ上の "ロック→ライブ復調開始" は **`is_true_lock()` を通ってから出すこと**。

## 8. 既知の未達 / 制約

- **映像＋音声のライブ復码は達成済み**（2026-09-26 実測）。ffmpeg が H.264
  (Constrained Baseline 320x180 15fps) + HE-AAC 48kHz stereo として認識し、
  実測キャプチャから 192 フレームをデコードした。**TS コンテナ経由の PAT 欠損問題
  は `--no-psi` を外す既定動作（psi 注入）で解消済み**（ffprobe が program を解決）。
  ただし **program_number の実測値は局ごとに違う**。札幌 NHK総合 = 10624
  （`PROGRAM_NO`）。ハードコード値が違うと ffmpeg が
  `no program with id NNNNN found` を出し program を解決しないので、確認すること。
- TS を**ファイルとして** ffprobe すると `non-existing PPS` / `no frame!` が出る件は、
  既定で有効の PSI 注入（PAT/PMT 合成）投入後は解消。`--no-psi` を付けた
  出力のみ残る。
- **保存した TS が再生できない問題（2026-09-26 解決済み）**。原因は字幕 PID
  0x0587 の PES ヘッダ長。下記 §8.2 参照。
- `stream_decode` のログが「ロック→ライブ復調開始」を出しても、Wayland 上の
  ffplay ウィンドウが出ないことがある。SDL/Xwayland の問題であり復調とは無関係。
- 音声 PES は HE-AAC / LATM で、PES header / CC は正常。ffplay 側で
  `channel element 3.1 is not allocated` 警告が出るが音は出る。

### 8.1 TS 品質の見方（2026-09-26 実測に基づく）

「RS ブロック 100%」というログは**品質保証にならない**。実測で判明した 3 点:

**(1) 訂正不能ブロックを null パケットに置き換える**（`stream.rs` `NULL_PACKET`）

旧実装は `if let Some(cw) = rs::decode(&ds) { out.push(cw) }` で、訂正不能
（`None`）だと 188 バイトが TS から消えていた。実測 RS: 82,329 ブロック中
126 本（0.15%）が対象。これは**帯域を保つ**ため null パターン
（PID 0x1FFF, 188 バイト 0xFF）を 1 本差し込む。demux 側は「1 パケット
読み飛ばした」と正しく判定し次へ進む。ただし 1seg 帯域では PID 0x1FFF は
本来 null 予約で、**放送の詰め物と区別がつかない**。999 本の null のうち
訂正不能由来は 126 本で、残り 873 本は詰め物。

**(2) RS 品質カウンタを公開**（`StreamingDecoder::rs_quality()`）

`rs_error_stats()` は「訂正した」数しか返さない。`rs_quality()` は 4 つを返す:

| 戻り値 | 意味 | 実測値 |
|---|---|---|
| `rs_corrected` | 訂正を要したブロック数 | 5,168（6.3%） |
| `rs_bit_errors` | 訂正を要したビット総数 | — |
| `rs_dropped` | 訂正不能で null に置換したブロック数 | 126（0.15%） |
| `rs_miscorrected` | 訂正後も syndrome 非ゼロのブロック数 | **0**（RS 復号器は健全） |

`ndec` は null パケットを数えない。訂正不能を「復号成功」に数えると終了ログが
100% を嘘く（実測: 修正前 5280/5280=100% → 修正後 5280/5406=97.7%）。

**(3) 収束ゲートは実装したが、既定は無効**（`ISDBT_GATE=1` で有効化）

H.264 MB エラー 20 件は**ストリーム冒頭に集中**（先頭 20 秒を捨てると 20→1）。
等化器収束説を検証するため出力ゲートを実装したが、実測で**効果がない**と判明:

| ゲート | MB エラー | 出力バイト |
|---|---|---|
| なし | 20 | 1,007,492 |
| 時間 2400 シンボル | 20 | 904,656 |
| 時間 12000 シンボル | 6 | 40,984 |
| 品質 200 連続無誤 | 0 | **0**（出力ゼロ）|
| 品質+fail-open 既定 | 0 | **0**（出力ゼロ）|

訂正不能は冒頭 51 個/チャンク → 以降 1〜4 個/チャンクへ減るものの**最後まで
消えず**、この信号では 20 連続（200 はともかく）無誤が一度も達成されなかった。
つまり MB エラーは「冒頭の等化器収束」だけでなく**散発的な復調 bit error**に
起因し、時間ゲートでは除去できない。品質ゲートだけだと出力がゼロになり
改善を阻むので、既定は無効とした。

**残課題: H.264 MB エラー 20 件（24 秒キャプチャ・192 フレーム中）の根因未特定。**
RS 訂正後 synd==0（誤訂正ゼロ）なのに H.264 が壊れる。訂正不能 null では説明
できない。候補: (a) 復調 bit error が訂正後も残る領域がある（synd 0 でも
実データが壊れる off-by-N の可能性未検証）、(b) 等化器の 1-tap 推定精度。
アンテナ/C/N 向上より先に、訂正『成功』ブロック内の bit error を直接数える
計装を足すのが次の一手。

**経路による差（2026-09-26 実測、同一キャプチャ）**:

| 経路 | 出力バイト | フレーム | MB エラー |
|---|---|---|---|
| ファイル（`stream_decode file.iq out.ts`） | 1,008,620 | 192 | 20 |
| パイプ（`rtl_sdr \| stream_decode`） | 1,610,784 | 19 | 0 |

パイプ経路は出力が実時間に対して断続的（1.6% 程度）で、デコード済みフレームが
少なくなるため MB エラーも少なく見える。ファイル経路が完全復調のベースライン。
パイプ経路の低出力は既知の制約（`docs/OPERATION.md` §4.1 の記述どおり、
`--follow` + ファイル経由なら実時間性能を維持できる）。

### 8.2 保存した TS が再生できない問題（2026-09-26 解決）

**症状**: `stream_decode` が出力した .ts を ffplay / VLC で開いても再生しない。
ffprobe も `format.duration = 86914 秒`（約 24 時間）を返す。

**原因**: 字幕 PID **0x0587**（`stream_id = 0xbd`、ARIB 字幕）の PTS が
生放送の絶対時刻 **7821034381（= 86900.4 秒 = 1日1時間後）** のまま残っていた。
`PtsNormalizer::normalize()` が対応する PES ヘッダ長を 5 / 7 / 10 しか
認識しておらず、この字幕の **hlen = 0x17 = 23** をスキップしていた。

実測の生バイト:
```
000001 bd 002e 80 81 17 2f48af07 1b8e4343495304bf
          ^^ ^^ ^^
          |  |  hlen=0x17=23
          |  flags2=0x81 (PTS あり)
          stream_id=0xbd
```
映像 0x0581 と音声 0x0583 は hlen=5 なので既に正規化されていた。字幕だけが
漏れていたため、**1 つの字幕 PES の巨大 PTS がコンテナ全体の duration を
污染し、TS 全体が再生不能になっていた**。

**証拠**: PID 0x0587 を TS から除去すると `duration` が 86914 → **18.9 秒**に
復帰し、正常に再生できた。

**修正**（`crates/isdbt-dsp/src/ts.rs` `PtsNormalizer::normalize`）:
`hlen != 5 && hlen != 7 && hlen != 10` に `&& hlen != 23` を追加。

**修正後の実測**:

| 項目 | 修正前 | 修正後 |
|---|---|---|
| `format.duration` | 86,914.9 秒 | **18.87 秒** |
| 字幕 start_time | 86,900.4 秒 | **3.45 秒** |
| 映像 start_time | 0.334 秒 | 0.334 秒 |
| 映像フレーム数 | — | 192 |
| ffplay 終了コード | 再生しない | **0（正常終了）** |

**教訓**: 1seg は PAT を欠くため demod 側で合成 PSI を注入する。この
とき**全ての PID の PTS を同じ方式で正規化しないと、1 つの未対応 stream が
コンテナ全体を壊す**。PES ヘッダ長 5/7/10/23 は ISDB-T 1seg の 4 形態
（映像=5 / 音声=7 / 字幕=23 / MPEG 標準=10）に対応している。

### 8.4 訂正不能ブロックの扱い — null packet 挿入は撤回（2026-09-26）

**症状**: VLC で再生すると、**再生時間とともに画像がこわれてゆく**。

**原因: null packet 挿入の撤回が必要だった。** 訂正不能 RS ブロックの
188 バイトを PID 0x1FFF の null パケットで埋める実装を入れていたが、
これが**映像 PES の途中に 188 バイトの穴を作る**。H.264 は参照フレーム方式なので
穴ごとに GOP 全体が破綻し、次の I フレームまで出画できない。
**TS 構造としては正しかった**（sync 0x47 あり、bitrate も保たれ、VLC の
buffer deadlock も消えた）のに、視聴すると壊れる。

**教訓**: TS 構造の検証（sync/CC/PCR が正しい）と、視聴品質は別物。
`ffmpeg -f null` で「フレーム数が取れる」「MB エラー数が少ない」だけでは
H.264 の参照フレーム破綻を検出できない。**実際に再生して時間経過を見る**
ことが必要。

#### 試行した 3 案と結果

| 案 | TS 構造 | 視聴 | 判定 |
|---|---|---|---|
| `[0xff; 188]`（sync なし）| **破綻**（sync 異常 34.6%）| VLC が読めない | 却下 |
| `null_packet()`（PID 0x1FFF）| 正常 | **時間とともに崩壊** | **撤回** |
| **穴を空ける**（出力しない）| 正常 | 時間とともに崩れない | **採用** |

現在の挙動: 訂正不能ブロックは出力しない。`ContinuityTracker` が CC を詰める
ので demux 側は欠落に気づかず、H.264 が repair される。終了ログが
`100.0%` に戻る（null を数えていないので `nblk == ndec`）。

#### 撤回後の実測（`oneseg_30s.ts`、26.8 秒）

MB エラーは**中央にピークして終端は 0**（単調増加ではない）:

| 区間 | MB エラー |
|---|---|
| 0-4 秒 | **0** |
| 4-8 秒 | 3 |
| 8-12 秒 | 11 |
| 12-16 秒 | 30 |
| 16-20 秒 | 32 |
| 20-24 秒 | 16 |
| 24-28 秒 | **0** |

累積障害（時間とともに単調増加）ではない。実放送の C/N 変動による
散発的な bit error で、訂正不能が塊になって現れたもの。冒頭に集中しないので
「等化器収束説」も支持されない。

#### 原因: I フレームが欠落する（2026-09-26 実測で確定）

**あなたの仮説が当たりだった。** 「最初はきれい、時間が立つと崩れる」の
仕組みは **I フレーム（キーフレーム）が取れていない**こと。

実測（`oneseg_30s.ts`、26.8 秒）:

| 区間 | 状態 |
|---|---|
| 0-16 秒 | I フレーム 10 個（2 秒間隔で正常）|
| **16-22 秒** | **I フレーム 0 個**（17・19・21 秒のはずが全部欠落）|
| 22 秒〜 | I フレーム 1 個（21.76 秒）|

I フレームの分布:
```
I@0.000  I@2.002  I@4.004  I@6.006  I@8.008
I@10.010 I@12.012 I@14.014 I@16.016
（16 秒以降 7 秒間まったく無い）  I@21.755
```

**GOP 間隔 2 秒** なので 18・20・22 秒に I フレームがあるはずが、
すべて消えている。H.264 は参照フレーム方式なので I フレームがないと
**その後の P フレームがすべて連鎖的に壊れる**。これが「時間とともに崩れる」。

#### なぜ I フレームが落ちるのか: 訂正不能ブロックの連続

実測: **訂正不能 RS ブロックが 51 個連続して 1 箇所で発生**（総 126、0.15%）。

1seg の構造:
- 1 フレーム = **64 RS ブロック**
- I フレームは 2 秒ごと = 約 **128 ブロック**周期

51 連続は**1 フレームの 80% を破壊**する。訂正不能ブロックは出力しない
ので（§8.4 の撤回）、その区間の TS が丸ごと消える → I フレームが
PES ごと落ちる → 以降 2 秒以上の GOP が参照フレーム不足で破綻。

TS 上の時間穴も同じ位置に出る（実測）:
```
穴: 15.549 → 15.816 (0.267 秒)
穴: 16.950 → 17.284 (0.334 秒)
穴: 18.952 → 21.088 (2.135 秒)   ← I フレーム欠落区間と一致
```

#### 真の結論

**訂正不能 0.15% が「散発的」出身ではなく「局所的に 51 個連続」している。**
これが I フレーム欠落 → GOP 破綻 → 時間とともに崩れる、という連鎖。

「RS 100%」表示は `nblk == ndec` なので**訂正不能を含めて 100%**に見えるが、
実際には 51 ブロック分（約 9.6 KB）が TS から消えている。`rs_dropped`
カウンタはこれを正しく区別している（`rs_quality()` の 4 番目）。

#### 対策 1: `discontinuity_indicator` — **実装済み（§8.5 参照）**
訂正不能が `BURST_THRESHOLD`=32 個以上**連続**したら、TS の先頭に
discontinuity 付き PCR パケットを 1 本挿入する。demux はそれを見て状態を
捨て、次の I フレームから回復する。**これが累積崩壊を防ぐ唯一の手段**。
（ISO/IEC 13818-1 §2.4.3.4 準拠、PCR_PID は映像 PID）

#### 対策 2: 訂正不能 51 連続の原因（C/N）— **未着手**
51 連続は 0.15% の平均から大きく外れた外れ値。アンテナ／C/N 向上で
消える可能性が高い。

### 4.4 30 秒の放送を TS に保存する（録音スクリプト）

`~/oneseg-rs/scripts/record30.sh` で 30 秒の実放送を TS に保存できる。

```bash
./scripts/record30.sh              # 札幌 NHK総合 ch15、30 秒 → oneseg_30s.ts
./scripts/record30.sh 473142857 60  # 周波数と秒数を指定
```

**重要: IQ をファイルに録ってから一括復調すること。** `rtl_sdr | stream_decode` を
直接パイプで繋ぐと `stream_decode` が実時間に追いつかず、TS 出力が実時間の
1.6% に落ちる（実測: 30 秒録音 → TS 2.07 秒しか出ない）。IQ ファイルを
中介させれば実時間の 1.5 倍で処理され、30 秒録音から 22〜33 秒の TS が得られる
（残差はロック/暖機の処理時間）。

30 秒録音の実測（札幌 NHK総合、TMCC 真ロック YES）:

| 項目 | 値 |
|---|---|
| IQ | 60,030,976 バイト（29.5 秒） |
| TS `duration` | 20.9〜33.7 秒（受信状態で変動） |
| 映像 | H.264 320x180 15fps、171〜345 フレーム |
| 音声 | HE-AAC 48kHz stereo |
| MB エラー | 20〜152（散発、限定的なアーティファクト） |

`duration` が 30 秒に届かないのは、IQ の先頭がロック/暖機に消費されるため。
IQ 29.5 秒 → TS 20.9 秒（71%）は 1seg 復調の実測性能。IQ を確実に
録れていれば（`--follow` でファイル末尾を追従しながら処理）、より
長く保存できる。

**残存する MB エラー**は全期間に均一に分布（ss=0 で 152、ss=30 で 25）。冒頭に
集中しないため等化器収束説ではなく**散発的な復調 bit error**。SN/C/N
向上が必要。アンテナ調整で改善する余地がある。
